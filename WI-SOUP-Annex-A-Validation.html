A.2 Which releases reached production

Three signals in a GitHub repository can be read as "this release went to production". They disagree, so the deployment record is used instead (WI §7.1, stage #4 step 1). Measured on one mobile product:

SignalRelease identifiedDate
Tag format (clean semver)v1.0.72025-10-01
GitHub prerelease flagv1.0.8-qa302026-05-04
Release asset named *production*v1.0.42025-06-23
Production deployment recordv1.0.72026-04-21

The three tag- and release-based signals span 315 days, and none matches the deployment record. A release date is not a deploy date: this product published v1.0.7 in October 2025 and deployed it to production in April 2026.

Two filters were required A production deployment whose ref is not a tag is not an application release. On one product the newest such record originates from a content-migration workflow, and using it would date the maintenance window grid from a database migration.

A repository with no production-equivalent environment reports unknown rather than broken. One product deploys to an environment named Study, which is equivalent to production for that product and is treated as such.

A.9 Defects found during implementation

Recorded because each was found by running the tooling against the repositories rather than by review, and because each was silent.

DefectEffect while present
Consolidation rebuilt the artifact component without its hashes and properties The image digest and build date did not reach the consolidated bundle, which is the document published as the release asset. The per-target files still carried them, so checking those did not reveal the loss.
select() inside a jq object constructor An empty optional policy field made the whole construction produce empty, so a monitoring run wrote a 0-byte evidence record while reporting success.
A greedy regular expression in Helm value resolution | default .Values.version won over the real key, resolving every image in a chart to the chart's default version. A pinned v1.2.4 would have been recorded as 1.0.0.
Escalation nested inside the KEV branch A breached deadline on a finding that was not in KEV produced no notification.
Document tier derived from github.ref_type ref_type is tag for a QA tag as well, so every staging build was marked as a release.
Raw scanner output left behind on the failure paths continue skipped the cleanup, so a failed scan left unnormalised files containing absolute machine paths.
The currency check was implemented but not called Two finding types, obsolescence and version distance, were never reported.
